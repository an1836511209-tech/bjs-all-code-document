# 对话自动命名反复超时

日志入口为 `suggest_conversation_title`，异常链为 ReadTimeout → APITimeoutError。标题使用与报告相同的模型，单独设置 20 秒请求超时和一次重试；没有输出长度限制。该功能与 BP 后台运行独立，异常被捕获后返回空标题，所以 `/api/conversations/title` 仍为 HTTP 200。

反复触发的代码原因：前端在模型返回前一直保留“新对话”标题，每轮成功提交都可能再次启动命名；没有请求中标记或失败冷却。模型或其网络链路持续缓慢时，每次都会产生完整堆栈。日志经过 HTTP 代理，但仅凭堆栈不能确定瓶颈在代理还是模型服务。

修复计划：立即显示本地兜底标题，每个聊天只尝试一次；标题请求无自动重试、限制输出、设置总耗时上限；同一服务最多一个命名请求，失败后冷却 5 分钟；降级仅记录简短信息，不把可选命名失败打印成主流程异常。

已实现：

- 前端在发出请求前立即保存并显示截取首条消息的兜底标题，持久化 titleAttempted 标记。后续消息和刷新都不会为同一个聊天重复命名；迟到的智能标题也不会覆盖已修改的标题。
- 标题模型请求设置 60 秒总预算、0 次自动重试及最多 64 个输出 token。标题接口同样以 60 秒为上限，前端在 65 秒中止，避免比服务端更早断开。失败始终保留兜底标题。
- 命名不进入主任务：报告提交并开始接收事件之后，前端才在后台发起标题请求，不等待它返回。服务端只占用标题接口自己的请求，不挡住 `/api/dev/runs`。
- 一个服务实例最多进行一个智能标题请求，其他请求直接降级；失败后冷却 300 秒，到期允许再次尝试，不累积请求队列。
- 预期降级仅记录错误类名和简短信息，不输出完整堆栈或供应商错误正文。主报告模型的超时和重试配置不变。

验证：11 项后端专项及异步运行测试通过，涵盖超时取消、冷却与恢复、并发请求以及标题等待时主任务可正常完成；3 项前端真实函数交互回归通过，涵盖重复调用、空智能标题和迟到回复保护。Ruff、相关文件类型检查、JavaScript 语法及差异空白检查通过。所有模型调用均使用模拟，未探测真实模型服务。

本次修复解决可选标题功能的重复触发和错误处理，不证明上游模型或代理链路已恢复。若上游一直不可用，标题将持续使用本地兜底，最多每 5 分钟尝试一次并记录一条简短信息。

生效需要重启 Report Agent 并刷新前端。无需重新上传材料或修改主报告超时配置。
