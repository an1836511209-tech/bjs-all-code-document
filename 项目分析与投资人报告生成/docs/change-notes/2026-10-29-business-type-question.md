# 一页纸业务类型判定的程序化交互

目标：材料无法判定产权/增资时，程序直接发出固定选择卡片，不依赖模型调用 ask_user 或包含特定关键词。回答仍属于原任务，并作为后续判定及模板渲染的依据。

计划：判定工具返回结构化 question_request；运行边界停止后续工具并透传卡片；持久化明确选择，拒绝不明确答案；渲染入口校验已确定的类型，避免模型绕过判定或用错模板。保留原材料读取错误，不能把解析失败伪装成业务选择题。

已实现：

- `detect_one_pager_business_type` 不能判定时直接返回结构化 `question_request`，包含业务类型 gate、固定选项和说明，无需模型追加 ask_user 或组织关键词。
- 中间件把判定调用与同批其他工具分离，收到 question_request 后结束本轮，不让模型继续猜测、重复提问或提前发布；运行服务直接持久化并向前端发出卡片。
- 卡片固定为“股权转让（产权）/增资扩股”。前端要求选择明确选项，允许同时填写补充说明。服务端也校验选择，拒绝“继续”“跳过”“两种都行”等模糊回答。
- 用户确认保存在原任务 `business_type_selection` 中，恢复后优先于文件名或模型参数；不能把模型自行填写的 user_hint 当作用户确认。后续判定读取已确认值，不再重复询问。
- 渲染工具要求任务已有明确业务类型，未判定则发同一卡片，传入另一类型则拒绝渲染；材料读取失败仍返回真实错误，不伪装成业务类型选择。
- 兼容旧的普通文字业务问题，并将识别到的类型问题归一化为同一 gate。

验证：34 项业务类型、工商补正、交互和异步运行回归通过；Ruff、相关文件类型检查及 JS 语法检查通过。独立无头 Chrome 用真实本地判定工具验证两种选择、必选提示、补充记忆、刷新保留以及同 task_id 继续；未调用 ask_user、真实模型或外部 MCP，浏览器异常为零。浏览器文档为合成产物，未发布真实报告。

测试入口：`apps/report_agent/tests/unit/test_business_type_question.py`；浏览器测试先运行 `frontend/tests/business_type_server.py`（本机 8020），再运行 `frontend/tests/business-type-question.cjs`（需 Playwright 与 Chrome）。

生效需要重启 Report Agent，并刷新前端。

## 后续修正：截图中的直接 ask_user 空白卡片

实际遗漏路径：Agent 绕过判定工具直接调用 ask_user，问题为“本项目属于哪种业务类型？”，选项为空且 allow_free_text=false。旧规则未覆盖“哪种”的措辞，并忽略了 context 中的“股权转让/增资扩股”，导致既无按钮又无输入框。此前只验证判定工具直接出卡片，没有覆盖这条直接提问入口。

修正：

- ask_user 工具出口统一归一化类型问题，结合问题及上下文识别，不允许将业务类型题输出为空选项。任何其他空选项问题也必须保留输入渠道，防止不可回答的卡片。
- 加载已保存的 pending_question 时修复旧结构，保留原 question_id、run_id，旧任务可以直接回答，不必重新上传。
- 前端对旧事件补充固定业务选项；重放缓存时采用服务端当前问题，避免旧空 payload 覆盖已修复快照。问题结构变化时重新渲染，保留用户草稿。
- 新增截图原始措辞、空选项且禁止输入、直接 ask_user、旧任务回答及旧缓存恢复回归；40 项相关测试通过。隔离浏览器验证旧空白卡片恢复为双选项并在同任务完成，脚本异常为零。未调用真实模型或自动替用户选择业务类型。
