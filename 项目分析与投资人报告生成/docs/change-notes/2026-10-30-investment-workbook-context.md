# 投资报告附件的正式名称与画像摘要关联

日期：2026-10-30。

已检查实际失败的投资报告任务：附件选项开启，材料、画像和标签证据都存在，附件 profiles 有一份、contexts 为零。原报告已完成。

原因有两处：画像调用使用了简称，返回画像已补正为正式全称，后续标签调用使用正式名称；标签输入还将画像精简为 JSON 摘要，省略了部分字段。旧附件记录器要求调用公司名称与画像 JSON 指纹都完全相同，因而没有保存关联。

## 修复边界

- 公司主体优先取已验证画像结果的正式名称，缺失时沿用调用参数；旧 profiles 读取时同样从原始证据校正，不模糊匹配名称。
- 完整画像指纹相同时保留原复用规则。摘要输入仅能绑定到同一轮、同一正式公司、同一材料版本下唯一的已验证画像；证券代码或信用代码有明确冲突时拒绝关联。
- 摘要绑定保存输入指纹与关联类型，并强制基于材料精选/核验标签，不能把来源为 LMS 的摘要输入直接当作免核验依据。主报告的 MCP 请求和响应不改写。
- 当前失败任务已利用本地成功调用记录中的 evidence_id、SHA 与原参数补回附件关联；没有重跑报告、调用模型或外部接口。主报告状态仍 completed。

投资报告的任务/产物元数据和材料/证据原本就有持久化；一页纸的 LangGraph 执行检查点是独立机制。附件任务与上下文由两条路由共用，不依赖原报告图检查点。

## 验证与使用

回归覆盖正式名称补正、JSON/文字摘要、持久化文件重开、证券代码冲突拒绝，以及投资报告通过独立附件任务完成导出且不新增原报告 run。原有异主体、材料哈希、失败隔离和附件校验测试继续执行。

重启 API 与附件 worker 后，在原对话点击“生成匹配表”或“重试附件”即可；无需重新生成投资报告。工作区中原有 Word 格式相关改动未修改。
