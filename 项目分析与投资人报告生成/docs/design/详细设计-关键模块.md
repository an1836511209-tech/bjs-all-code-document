# 投资报告与一页纸关键模块详细设计

版本：V1.0（配套评审稿） 日期：2026-11-05

本文补充概要设计中的关键流程与边界。标注“建议”的数据结构和行为属于目标设计，并非声称代码已经实现；现有入口以仓库代码为准。

## 1. 运行与确认状态

现有application/runs.py虽保留SynchronousRunService命名，实际存在asyncio.create_task后台执行、resume与cancel逻辑。API提供运行查询与事件流。不要按类名或旧README判断运行模式。

建议业务状态为：材料待补充、数据处理中、等待画像确认、投资人处理中、等待名单确认、内容生成中、审查中、等待报告确认、发布中、已交付、失败、已取消。该业务状态不直接替换现有run.status字符串，宜单独维护stage。

每个确认节点保存question_id、输入版本、问题类型、候选内容摘要、用户回答、回答人和时间。resume先校验任务归属、问题仍有效、回答类型匹配；重复回答相同question_id返回已有结果，不重复执行。上游企业、业务类型、材料变更时，作废相关画像、名单、估值与报告确认。

建议状态推进规则：

```text
收到答案
  -> 校验当前等待问题和输入版本
  -> 保存答案与新的内容版本
  -> 失效依赖该字段的下游结果
  -> 从最早受影响阶段继续
  -> 先落盘阶段结果，再发布阶段完成事件
```

后台任务退出不等于业务成功。用户等待、取消、失败和已交付必须分别展示。生产扩展建议采用持久化任务记录与带租约的worker，避免多个进程重复领取；当前代码不能据asyncio推定已具有该能力。

## 2. 材料与证据

现有入口为infrastructure/materials/parser.py、conversion.py、http_recognition.py及infrastructure/evidence/workspace.py。

材料处理顺序：验证类型/大小→生成材料标识与内容哈希→按格式提取正文表格或OCR→保存解析结果→按章节抽取字段→保留原始定位→完整性检查。

建议字段记录采用：field_name、value、source_type、material_id/evidence_id、page_or_section、observed_at、confidence、confirmation_version。字段有冲突时保留所有候选及最终选择，股权结构按需规优先材料。

建议Evidence复用键包含project_id、material_hashes、parser_version、company_identity、business_type。投资人名单额外包含profile_version、tag_version和selection_version。复用时必须验证权限与版本；公司同名或文件同名不足以证明同项目。

证据分为原始材料、外部查询、内部数据、人工修订和AI推断。引用校验检查证据存在、定位可解析以及正文与证据基本一致。没有直接证据的推断必须明确标注，不允许虚构来源链接。

## 3. 数据网关及错误处理

现有application/data_gateway.py、infrastructure/mcp/contracts.py与Data MCP的mcp/server.py负责边界。调用前后均按JSON Schema校验，完整结果写Evidence，模型读取简要视图后按需读取全文。

| 状态 | 编排动作 | 报告表达 |
|---|---|---|
| success | 使用通过校验的结果 | 按事实引用 |
| partial | 使用有效部分并记录缺项 | 明确限制 |
| empty | 不生成该类事实 | 未检索到可用结果 |
| failed | 判断是否可重试或转人工 | 数据获取失败，不能写成无相关事实 |

建议区分传输超时、限流、认证失败、契约不匹配和业务无结果。仅超时/限流等临时故障有限重试；契约不匹配立即阻止消费。重试次数与耗时上限配置化，日志记录run_id、tool、耗时及状态，不记录密钥。

搜索补充计数按项目和输入版本记录，最多一次补充检索；该限制与网络请求重试是不同概念。补充后仍缺失的维度进入缺项清单。

## 4. 投资人筛选算法

实现位置：apps/data_mcp/src/data_mcp/features/investor_match/。数据契约为match_investors.json。

目标算法：取得内部候选与网络候选→统一机构名称及可用标识→按工商股东集合排除→来源内去重→来源间合并→保留匹配理由与来源→排序→人工选择→输出数量限制。

同一机构两个来源均命中时保留双来源，不重复计数。名称模糊近似不能直接合并，应保存待确认关系。股东数据缺失时标记过滤未完成，不能把“无股东返回”解释为“已成功剔除全部股东”。

自然人不得进入机构candidates明细，只以计数输出。报告终稿内部前20、网络前10；一页纸内部候选前100供选择。计数应明确是检索数、过滤后数还是最终选择数，前端标题与导出保持一致。

现有shareholder_filter_applied用于表达过滤是否真实执行；输出生成必须消费该字段。机构工作簿辅助导出与报告主产物分离，辅助任务失败不应把已成功主报告改成失败，也不能虚报辅助文件完成。

## 5. 估值计算与样本

上市公司匹配实现位于features/listed_peer_match/，历史估值位于features/historical_valuation/。现有上市公司检索含权重、召回和重排能力，契约中的final_score为排名分，不是估值指标或投资推荐概率。

建议拆分“展示相关公司排序”与“估值统计全量样本”。前者可取Top N，后者按需规读取全部合格记录并分页处理，记录初始样本数、剔除数、有效数及原因。不能将召回Top N直接替代全样本统计。

历史样本匹配伪代码：

```text
dataset = confirmed_business_type对应的数据集
for row in dataset:
    overlap = intersection(normalized_project_tags, normalized_row_tags)
    if overlap为空: continue
    if required_financial_fields缺失: 记录剔除原因; continue
    保存row与overlap数量
按overlap数量降序并以稳定项目标识作为同分次序
按规模、受让方类型分组计算有效指标
```

数值建议使用Decimal；统一金额单位、时点和股权比例。指标分母为零、负利润、币种不一致与交易金额口径不明，分别标记不可用原因。PE/PB/PS的分子口径、增资前后估值、规模分组阈值及异常值规则需业务评审后版本化；本设计不擅定公式口径。

## 6. 一页纸内容与模板

现有domain/one_pager.py区分产权和增资，模板位于skills/one-pager/assets/。产权使用转让底价；增资使用对应持股比例、拟募集金额，两组交易字段互斥。业务类型识别有材料关键词、文件名和用户输入路径，冲突时应人工确认且保留最终选择。

必须统一域模型、preflight、写作规则和测试中的字数策略。目前one-pager-fields.md采用更长的正文建议值，与需规有实质差异。目标采用简介≤100、介绍每条80—150、亮点每条50—100，并明确统计字符是否排除空白、引用标记和标点。建议沿用去空白及来源标记的计数方式，但标点口径需在验收用例中固定。

介绍和亮点分别固定3条，简介、交易字段、联系人及名单保留缺失提示。现有风险识别与展示选择分离；用户选择不展示风险时保留内部证据和选择记录，不能声称原材料无风险。财务/风险条件槽位属于当前模板行为，需与需规的自由维度要求一并评审。

模板生成后检查占位符无残留、字段互斥、段落数量、来源可解析、文本框溢出及实际页数。超过一页时回到内容压缩与布局调整，不以任意缩小字号完成验收。修订内容后重新检查字数、事实及合规。

## 7. 审查、确认与发布一致性

现有质量入口为application/review_checker.py、ideology_review.py；Word处理为infrastructure/word/。建议将内容哈希作为审查与人工确认绑定对象。

```text
内容版本v -> 事实/结构复核 -> 合规审查 -> 人工确认v
-> 生成DOCX -> OOXML与批注校验 -> 渲染校验
-> staging -> 对象上传 -> 保存PublishedArtifact -> 返回下载信息
```

若任何环节修改正文，生成新版本并重新执行受影响审查；不得用旧版本确认发布新内容。合规改写不得修改财务数值、企业名称和引用关系；改写后再次检查。

发布失败保留可重试的staging及失败阶段；以内容哈希和模板版本支持幂等。对象上传成功而元数据落库失败时应补偿或对账，避免孤儿对象。数据库成功但下载链接过期时应重新授权生成链接，不能重跑整个报告。

导出文件名采用业务名称和年月日时间戳，时区统一Asia/Shanghai；内部产物保留唯一artifact_id避免同日覆盖。仅PublishedArtifact真实存在且存储成功后展示“已发布”。

## 8. 建议新增业务元数据

以下为逻辑设计，不是已执行DDL。

| 实体 | 关键字段 | 约束 |
|---|---|---|
| project_snapshot | project_id、version、company_identity、business_type、material_hashes | 项目与版本唯一 |
| confirmation | project_id、stage、input_hash、question_id、answer、actor、time | question_id幂等；旧版本不可确认新内容 |
| investor_selection | project_id、profile_version、candidate_version、selected_ids | 来源可追溯；自然人不存展示明细 |
| review_record | content_hash、rule_version、status、issues、reviewed_at | 审查只对绑定版本有效 |
| delivery_revision | artifact_id、content_hash、template_version、confirmation_id | 可追溯至最终确认 |

存储实现可先扩展工作空间结构，再按查询与一致性需要迁入MySQL。不能在未经迁移评审时直接写入生产DDL。

## 9. 验证用例与落地顺序

| 场景 | 核心断言 |
|---|---|
| 企业名称冲突后用户更正 | 重新查询企业数据，旧画像和名单不可复用 |
| 相同问题重复提交 | 不重复产生运行与产物 |
| 材料不足 | 停止写作且给出明确缺项 |
| 工商超时/股东过滤未执行 | 提示未完成过滤，不宣称无股东候选 |
| 自然人候选存在 | 页面、日志展示及Word无个人明细泄露 |
| 名单跨来源重复 | 最终去重且保留多来源 |
| 一页纸80/150、50/100边界 | 边界通过，越界修订；三个段落独立计算 |
| 可比样本超过单页 | 分页累计全量统计，不截断为排名列表 |
| 人工修改已审报告 | 旧审查与确认失效 |
| 取消、进程重启、事件重连 | 状态明确且无重复发布；跨进程恢复单独验收 |
| 上传成功而元数据失败 | 对账补偿可定位孤儿文件 |
| Word单页检查 | 无空白页、溢出、遮挡和未替换占位符 |

实施顺序：统一业务规则→完善版本/确认→补齐数据筛选与统计→建立发布门禁→完成真实系统联调及视觉验收。本次仅产出设计文档，未修改业务代码、配置或数据库，未运行业务测试。
