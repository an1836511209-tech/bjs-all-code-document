# 2026-10-22 生产排查

当天生产上连续出现三件看起来像同一次失败的事：投资人工具崩溃、Word 里机构表只有一行、个人接口的 `limit` 永远是 1。它们分别在 data-mcp 的返回裁剪、data-mcp 的配置加载、report-agent 的 Markdown 解析里。只更新其中一个镜像，另一个问题还在。

## 1. 机构名单不要带回 `label_name_list`

旧的 `query_dmp_investors` 使用 `limit=200`。`_map_institution_items` 把整份 `label_name_list` 写进 `match_reason`，并保留整条 `raw`。引用的 `quote` 再抄一遍 `match_reason`。一次机构响应大约 485KB，送回 Report Agent 的工具结果会到 1MB 以上。

MCP Streamable HTTP 客户端在回传时失败，日志只有：

`ExceptionGroup: unhandled errors in a TaskGroup (1 sub-exception)`

`str(ExceptionGroup)` 不会带上子异常。业务代码里没有 `TaskGroup`。这不是模型上下文超限：工具在大约 2.4 秒内失败，候选名单没有进入对话。

现在的约定在 `apps/data_mcp/src/data_mcp/features/investor_match/dmp_client.py`：

- 机构条目只留 `investor_name`、`match_label_num`、`match_label_weight_sum`。
- `match_reason` 只写「匹配标签数、权重和」。
- 不保留 `raw`，不保留 `label_name_list`。
- 交给后续流程的机构名单最多 `AGENT_INSTITUTION_LIMIT`（30）条。
- 个人响应只读 `body.count`，不读 `items`、`total`、`totalResults`。

Agent 看到的个人数量字段是 `data.counts.internal_individuals_excluded`，命令行结果里是 `internal.individual_count`。个人不进 `institutions` 和 `merged`。

`body.count` 是这一页返回的条数，不是全部个人投资人的总数。`individual_limit` 设成 1 时，这个数就是 1。把它调到 500，读到的仍是本页条数，上限 500。

## 2. yaml 里的 offset / limit 必须进加载结果

`deploy/environments/prod/data-mcp.yaml` 的 `investor_match.dmp` 可以写：

```yaml
institution_offset: 0
institution_limit: 30
individual_offset: 0
individual_limit: 500
```

容器里 `grep` 能看到这些行，只说明文件挂进去了。2026-10-22 的镜像里，`load_investor_match_config` 重组 `dmp` 时只复制了地址、鉴权和超时，这四项被丢掉。进程里读出来是 `None`，请求使用代码默认值：机构 `offset 0 / limit 30`，个人 `offset 0 / limit 1`。

机构入参看起来「配置生效了」，是因为代码默认的 `limit` 正好也是 30。个人请求体一直是 `"offset": 0, "limit": 1`。

修复在 `apps/data_mcp/src/data_mcp/shared/settings.py`：`_page_setting` 把这四项读成整数，放进返回的 `dmp`。缺省或非法时不写入，由 `dmp_client._page_params` 使用默认值。个人默认 `limit` 仍是 1，机构默认是 30。

改这四个数字只需要更新挂载的 yaml，前提是运行中的 data-mcp 镜像已经包含上述加载逻辑。旧镜像改 yaml 不会改变请求体。

容器内确认（不要打印整份 yaml，里面有口令）：

```bash
docker-compose --env-file deploy/environments/prod/runtime.env exec data-mcp \
  python -c 'from data_mcp.shared.settings import load_investor_match_config; d=load_investor_match_config()["dmp"];
[print(k, d.get(k)) for k in ("institution_offset","institution_limit","individual_offset","individual_limit")]'
```

期望能看到 yaml 里的四个整数，而不是 `None`。

## 3. Word 机构表只有一行时，先看 Markdown 里的引用位置

写作说明要求表格每一行后面写 `<!-- cite: evidence_... -->`。`report-outline.md` 的示例就是一行公司加一条引用。模型照做时，`report.md` 里会有全部机构，但旧的 `md_parser.py` 把任何非 `|` 行都当成表格结束。

结果是：表头加第一行收成一张表；后面每一行被当成新表头，紧接着的引用把空表丢掉。docx 只有第一家。`create_word_from_md` 仍返回 `valid: true`。上市公司对标表、同类成交表同样会只剩第一行。

引用写在整张表最后一行后面时，旧解析器会保留所有行。所以同一套 report-agent，有的报告能画出全部机构，有的只有一行。差别在当次 Markdown，不在 data-mcp 返回了几条。

2026-10-22 的一次运行里，data-mcp 已返回 30 家机构、个人数量 500，Markdown 里写了 29 家，每一行后都有引用。docx 仍只有一行，因为当时只更新了 data-mcp，report-agent 还是旧解析器。

修复在 `apps/report_agent/src/report_agent/infrastructure/word/md_parser.py`：表格还开着时，引用注释记到当前未标注的行上，不结束表格。表写完后的那一条引用仍然覆盖尚未标注的行。不要把行间引用再改回「遇到就 flush」。

用当前解析器解析那次「每行一条引用」的原文，得到 29 行。生产 docx 只有 1 行时，生成它的 report-agent 镜像还没有这段逻辑。

## 4. 发布时两个镜像分开换

| 改动 | 要更新的镜像 | yaml 挂载够不够 |
| --- | --- | --- |
| 机构裁剪、个人只取 count、分页字段加载 | `bjs-data-mcp:0.1.0` | 分页数字在新镜像上改 yaml 即可；加载逻辑本身必须在镜像里 |
| Word 行间引用 | `bjs-report-agent:0.1.0` | 不够 |

`docker load` 只更新镜像标签，不替换正在跑的容器。只换 data-mcp 时，在运行目录执行：

```bash
docker load -i bjs-investment-report-images.tar
docker-compose --env-file deploy/environments/prod/runtime.env up -d --no-deps data-mcp
```

只换 report-agent 时把服务名换成 `report-agent`。打包也只 save 对应的镜像。

不要用下面这组做这种单服务更新：

- `run --rm report-agent report-agent-db-migrate --apply`：这次没有表结构变化。
- 不带服务名的 `up -d`：镜像或配置有差异时会把另一个服务也重建。

report-agent 依赖 data-mcp。`--no-deps` 避免把另一个服务一起拉起来。被换掉的那个服务在重启完成前，新的调用会失败；另一个容器保持原进程。

确认时看 `ps` 的创建时间：只应有目标服务是刚才创建的。
