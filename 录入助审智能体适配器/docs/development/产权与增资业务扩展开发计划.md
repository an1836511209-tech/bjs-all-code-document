# 产权转让与企业增资分披露阶段业务扩展开发计划

编制及修订日期：2026-10-27。状态：方案草案，已结合当前仓库代码梳理；尚未实施业务代码变更。本版按最新确认，将原两个独立类型细分为四个类型，并新增材料业务及披露阶段匹配校验。

## 1. 目标与范围

按最新确认，新增以下四个独立业务类型。保留现有四类实物业务，最终共八类：

| 业务类型 | 本次范围 |
| --- | --- |
| 有纸大宗实物 | 兼容与回归 |
| 无纸大宗实物 | 兼容与回归 |
| 有纸小宗实物 | 兼容与回归 |
| 无纸小宗实物 | 兼容与回归 |
| 产权转让-预披露 | 新增匹配校验、材料分类、字段提取、字段审核、文件审核及溯源 |
| 产权转让-正式披露 | 新增匹配校验、材料分类、字段提取、字段审核、文件审核及溯源 |
| 企业增资-预披露 | 新增匹配校验、材料分类、字段提取、字段审核、文件审核及溯源 |
| 企业增资-正式披露 | 新增匹配校验、材料分类、字段提取、字段审核、文件审核及溯源 |

四个新类型不再按有纸/无纸、大宗/小宗展开。预披露与正式披露分别配置字段、材料必需性和审核口径，不能只修改类型名称或直接共用全部规则，也不能从现有无纸业务推导为默认通过。不将原草案中的 `产权`、`增资` 作为四个新类型的有效调用值，避免缺少披露阶段。

新增明确要求：调用方传入的业务类型必须与实际文件内容匹配。例如，传入 `产权转让-预披露` 却上传企业增资申请材料，提取、审核接口均应终止处理并返回可定位的错误，不自动切换为增资业务，也不作为普通字段“待确认”继续执行。

交付覆盖本仓库的 API、任务查询、规则管理页面、配置文件、测试和接口文档。上游业务系统的录入页面与调用参数需要协同联调，其开发工时另计。

## 2. 当前实现与影响

| 当前实现 | 位置 | 对方案的影响 |
| --- | --- | --- |
| `BusinessType` 仅包含四类实物 | `src/schemas/rule_config.py` | 增加四个枚举，保持原四个值不变 |
| 类型到规则配置的映射是独立字典 | `src/utils/extraction_type_mapper.py` | 提取、审核共用，需一并扩展，支持类型提示应由同一来源生成 |
| 显式传配置 ID 时直接加载配置 | `src/services/extraction/service.py`、`src/services/audit/service.py` | 增加配置存在、启用、业务类型匹配校验，防止跨品类调用 |
| 默认规则取同业务下最新更新的启用配置 | `src/services/rule_config_service.py` | 新类型首期各发布一套启用配置；不同时启用未验收候选版本 |
| 规则以 JSON 保存 | `data/rule_configs/` | 首期无需引入数据库迁移，需要四个新配置与部署备份方案 |
| 业务下拉从枚举生成，材料下拉从标签生成 | `src/api/v1/endpoints/rule_config_web.py` | 核对枚举扩展后的创建、筛选、编辑流程，无需另造一套管理页面 |
| 文件分类有独立 API 与中台映射两条路径 | `src/services/classification/service.py`、`src/services/classification_service.py` | 文件类型、关键词、中台材料编码、LLM 分类输出需同步适配 |
| 现有文件分类主要返回材料种类，不能据此证明业务与披露阶段匹配 | `src/schemas/classification.py`、`src/services/llm/client.py` | 增加内容级业务识别与匹配校验，区分材料种类、业务类别、披露阶段 |
| 当前任务查询主要提供字符串错误信息 | `src/schemas/task.py`、`src/services/task_store.py`、`src/api/v1/endpoints/task.py` | 增加可选结构化错误，确保超时后的查询也能获得一致错误码和文件详情 |
| HTTP 异常处理器当前仅保留错误码和消息等有限属性 | `src/main.py` | 显式保留文件详情及追踪标识，避免结构化错误在统一包装时丢失 |
| 提取用全局级联集合识别字段，审核过滤按业务类型查级联 | `src/services/extraction/cascade_configs.py`、`src/utils/field_value_converter.py` | 新业务应按业务类型选择级联，防止字段同名导致误触发或过滤不一致 |
| 提取结果和审核复用提取结果时，仅按文件内容哈希查询缓存 | `src/utils/file_hash.py`、`src/services/task_store.py`、提取及审核服务 | 必须隔离业务类型和规则内容，防止同一营业执照等附件产生跨业务缓存命中 |

现有四套配置约含 48～82 个提取字段、50～81 条审核规则。新品类工作量主要取决于四个场景的字段表、审核口径、材料内容识别和样本覆盖情况，不能只按增加四个枚举估算。

## 3. 实现方案

### 3.1 类型与接口

- 新增枚举成员及对外值：`PROPERTY_TRANSFER_PRE = "产权转让-预披露"`、`PROPERTY_TRANSFER_FORMAL = "产权转让-正式披露"`、`CAPITAL_INCREASE_PRE = "企业增资-预披露"`、`CAPITAL_INCREASE_FORMAL = "企业增资-正式披露"`。
- 沿用请求中的 `extraction_type`、`audit_type`、规则配置中的 `business_type`，不新增必填维度。
- 内部统一解析业务类别（产权转让/企业增资）和披露阶段（预披露/正式披露），用于规则选择、材料匹配、级联与缓存；对外仍使用上述完整字符串。
- 沿用当前同步等待及超时后任务查询方式、溯源返回格式。本次检查的提取/审核路由主要为同步接口，不将新增流式接口作为本次必交功能；如部署另有流式入口，也应接入同一校验并透传错误。
- 将规则解析和校验集中为统一入口，供提前统计字段数、实际提取、审核及缓存查询使用；一次请求固定使用同一份配置快照。
- 无配置、配置禁用、类型不匹配时返回明确业务错误。相关检查在复用缓存之前完成。
- 提取和审核共用材料匹配校验。审核即使已传 `confirmed_fields`、`rule_config_id` 或有历史提取结果，也不能跳过材料业务校验。
- 同一个正在执行的任务 ID 若被用于不同业务或规则，应拒绝为冲突，避免返回其他业务的任务；保留同一请求的正常重复调用行为。

### 3.2 材料与分类

先建立“正式材料名称—FileType—中文标签—中台材料编码—别名—业务类别—适用披露阶段—核心/通用/参考材料角色—必交条件”对照表，再扩展代码。

- 可复用材料候选：营业执照、评估报告、评估备案/核准文件、内部决议、信息披露申请书。
- 待确认新材料候选：公司章程、审计报告、财务报表、股东信息材料、增资方案等。只有确实需要独立提取或审核的材料才新增文件类型。
- 产权交易业务与现有 `property_certificate`（房屋产权证）含义不同，不能直接用该文件类型代表产权业务材料。
- 对四个场景的申请书、披露文件等核心材料建立可区分的映射；营业执照、审计报告等通用材料可以跨业务复用，不能仅因其通用而判定类型不匹配。
- 同步核对文件名分类、中台编码映射、LLM 分类能力与 `MaterialResolver` 的材料匹配。未知材料保留“其他文件”处理与人工确认途径。

以上为需求梳理候选项，不代表正式材料必交要求。

### 3.3 四套业务规则

分别交付四个场景的字段字典、提取规则、审核规则、级联关系及样本预期结果。可复用经过确认的公共规则，最终发布为四份独立配置，不直接复制实物规则后批量改名。

| 业务 | 候选字段组 | 候选审核点 |
| --- | --- | --- |
| 产权转让-预披露 | 项目及标的企业、转让方、拟转让股权等预披露字段 | 预披露材料与主体一致性；拟转让信息一致性；按预披露口径处理尚未确定的信息 |
| 产权转让-正式披露 | 项目及标的企业、转让方、股权比例、财务/评估、转让价格、交易条件 | 正式披露材料完整性；比例、金额单位、基准日期；价格及交易条件与材料一致性 |
| 企业增资-预披露 | 融资企业、现有股东、拟增资安排、投资方要求等预披露字段 | 融资主体与预披露材料一致性；拟增资安排一致性；按预披露口径处理尚未确定的信息 |
| 企业增资-正式披露 | 融资企业、股东、拟募集资金、拟新增注册资本、拟释放股权比例、投资方要求、遴选条件 | 正式披露材料完整性；金额和比例口径；增资前后关系；方案、决议与披露内容一致性 |

字段编码、必填性、枚举值、金额精度、比例单位、日期口径、材料优先级均以业务提供并确认的表格为准。公式校验先确认分母、币种、时点和例外条件，再实现确定性校验。

每条审核规则明确材料缺失、字段为空、来源冲突、解析失败、不适用五种情况的处理方式。`auto_pass_when_missing` 仅在已确认的具体规则上使用。

多股东、多转让方、跨年度财务表应在需求阶段确认是否要求逐行结构化结果。当前配置字段类型只有文本、单选、多选，虽然部分请求/结果可承载 JSON，仍需验证配置、提取、审核、展示和溯源整条链路；不得直接认定已支持重复明细。若首期必须支持，单列模型和链路扩展任务。

### 3.4 材料业务及披露阶段匹配校验（新增重点）

#### 校验链路

```text
请求参数与规则校验 → 下载/复用解析内容 → 文件内容识别 → 材料集合匹配校验
  → 匹配通过 → 查询业务结果缓存 → 字段提取或审核 → 溯源与结果返回
  → 不匹配/无法确认 → 返回明确错误、任务失败，不执行后续提取或审核
```

- 建议新增共享组件 `src/services/business_validation/service.py` 及对应内部模型，由提取、审核服务统一调用，不要求调用方先请求独立分类接口。
- 每个文件识别：材料种类、业务类别、披露阶段、材料角色、识别状态、判定依据及来源页码/片段。无法确定类别或阶段时显式记录“未知”，不强行归类到请求类型。
- 文件名、调用方 `file_type`、中台编码仅作为线索；即使编码或文件名显示“产权转让”，也要核对实际正文。业务识别应独立输出实际类别，再与请求比较，不能让请求值直接决定识别结论。
- 结合封面/标题、表单章节及正文中的核心业务内容判断；文件改名、共用模板、引用其他业务词语不应造成误判。前两页证据不足时继续定位相关章节，不能仅凭前两页或单一关键词下结论。
- 优先采用明确模板特征与可核对的内容证据，模糊情况再由 LLM 辅助识别；置信度阈值由四场景标注样本校准，不能把模型自报分数直接当作正确性保证。
- 同时执行文件级和材料集合级校验。多文件中混入不兼容的业务专属材料时整体拒绝，不仅检查第一份；合并 PDF 内含不同业务材料时，按可识别的文档片段检查。

#### 处理策略

| 场景 | 行为与建议错误码 |
| --- | --- |
| 请求产权转让，核心材料正文明确属于企业增资，或反向情况 | 拒绝整个请求，`BUSINESS_TYPE_MISMATCH` |
| 业务一致，但核心材料明确为不兼容的另一披露阶段 | 拒绝整个请求，`DISCLOSURE_STAGE_MISMATCH` |
| 材料集合混入其他业务或不兼容阶段的专属材料 | 拒绝整个请求，`MATERIAL_SET_CONFLICT`，逐项列出文件及冲突原因 |
| 正式披露项目附带预披露历史材料 | 按业务确认的“核心/历史参考材料”兼容矩阵处理；允许的参考材料不触发阶段错误，也不能替代正式披露核心材料 |
| 营业执照、审计报告等通用材料，本身无披露阶段 | 按通用材料处理，不强制归类；结合核心材料确认请求类别与阶段 |
| 只上传通用材料，或内容证据不足以确认请求场景 | 若该场景缺少必要核心材料，返回 `REQUIRED_MATERIAL_MISSING`；核心材料存在但仍无法确认时返回 `MATERIAL_BUSINESS_UNDETERMINED`，提示补充或更换材料 |
| 文件无法解析、OCR/识别服务失败 | 返回独立技术错误及可重试提示，不能伪装为业务不匹配，也不能默认校验通过 |

四个新场景分别确认用于识别类别和阶段的核心材料要求。明确识别到企业增资、但无法确定披露阶段时，仍足以拒绝产权转让请求；错误中只填写已识别出的信息，不编造阶段。

#### 错误返回约定

建议沿用现有统一错误外壳。同步等待期间识别到材料不匹配时返回 HTTP 400，业务错误码区分具体原因。以下为**拟新增的契约示例**：

```json
{
  "code": 400,
  "message": "材料业务类型与请求不匹配",
  "trace_id": "trace_example",
  "error": {
    "error_code": "BUSINESS_TYPE_MISMATCH",
    "error_message": "请求类型为产权转让-预披露，附件正文识别为企业增资材料，请核对业务类型或更换附件。",
    "details": [
      {
        "field": "files[0]",
        "message": "附件标题及正文表明该文件用于企业增资。",
        "file_name": "项目申请书.pdf",
        "expected_business_type": "产权转让-预披露",
        "detected_business_category": "企业增资",
        "detected_disclosure_stage": null,
        "page_number": 1,
        "evidence": "企业增资信息披露申请书"
      }
    ]
  }
}
```

- `ErrorDetail` 当前只有 `field`、`message`，实现时需增加示例中的可选属性，或定义专用详情模型；不能仅返回一段调用方无法解析的字符串。
- 当前提取/审核路由存在通用异常捕获，需要增加可识别的业务异常并保留错误码和详情，避免被改写为 HTTP 500。
- `src/main.py` 的 HTTP 异常处理器目前未透传 `details`，需同步调整，保留模型约定的详情及顶层 `trace_id`，并验证接口实际返回结果。
- 若初始接口因超时已返回 `pending`，后续校验失败应将任务置为 `failed`；任务查询成功本身仍可返回 HTTP 200，但 `data.status = "failed"`，保留 `error_message` 并新增可选 `data.error` 返回同一结构化错误。内部任务模型、Redis 序列化、任务更新和查询返回均需适配，兼容旧任务无此字段。
- 接入平台网关时，为新业务错误维护明确映射，保留详情，不被映射成成功或未知内部异常。如有流式入口，返回同一错误内容并终止流。
- 不匹配结果不写入成功提取缓存，不返回部分提取或通过的审核结果，不自动修改请求业务类型。日志记录请求标识、文件、期望/识别类别和阶段及简短依据。

### 3.5 缓存、级联与兼容

提取结果缓存使用独立的业务缓存标识，建议包含：

```text
提取缓存标识 = hash(
  完整业务类型（含披露阶段） + 配置ID + 有效规则内容指纹 + 材料校验策略指纹 +
  规范化附件清单（文件内容哈希、材料类型及影响匹配的文件名）
)
```

- 保留纯文件内容哈希的用途；对提取结果索引、查询、审核复用和相关分布式锁统一使用新的标识。
- 内容指纹基于实际生效规则和相关级联配置生成，避免只依赖当前可能未随编辑变化的版本号。
- 原始解析缓存按其实际解析输入复用；业务结果缓存必须区分品类和规则。
- 材料内容识别缓存按内容哈希及识别器版本隔离；集合匹配结果还应包含期望业务/阶段、材料角色和兼容策略指纹。未标明校验通过及策略版本的历史业务结果不得绕过校验直接返回。
- 新索引使用新命名空间，遇到旧结果缺少业务/规则标识时不直接复用，历史任务仍可按任务 ID 查询。
- 提取和审核使用相同的业务级联注册来源。四类实物的原有关系保持等效；四个新场景分别启用经确认的关系。
- 新增严格材料业务校验首期覆盖四个新场景，现有四类实物按原业务口径回归；共性配置及缓存隔离改动同步验证旧业务兼容性。
- 不引入全面三维业务模型重构，也不为四个类型各复制一套服务。

## 4. 开发任务与顺序

以下为修订后的初步工程估算，前提是四场景字段表、材料样本和审核口径可及时提供。合计约 18～25 个开发人日，单名后端主开发配合业务及测试约 4～5 周；需求反复、上游系统开发和结构化重复明细另计。较原草案增加了披露阶段差异配置、内容级材料校验及结构化错误链路。

| 阶段 | 任务 | 交付物与完成条件 | 估算 |
| --- | --- | --- | --- |
| P0 需求冻结 | 四场景字段、材料、审核、级联、多行数据；中台编码、核心材料和阶段兼容矩阵 | 四场景规则矩阵、代表样本、错配样本及标准答案 | 2 人日 |

依赖顺序：P0 → P1 → P2 → P3 → P4。需求表和样本整理可与共性技术梳理同步进行；未经确认的审核口径不作为正式规则发布。

如果 P0 确认必须新增重复明细结构，暂追加 3～5 个开发人日，具体依据行级审核、跨页表格和逐行溯源范围重新估算。

## 5. 验收与测试

### 自动化验证

1. 八种业务类型均可映射、创建规则、按类型筛选；现有四份 JSON 可正常加载；四个新值必须包含披露阶段。
2. 四个新场景分别支持默认规则与显式配置；未知类型、配置缺失/禁用/不匹配有明确错误。
3. 同附件跨业务、跨披露阶段、跨配置、同配置修改内容或校验策略更新不复用过期结果；相同业务、阶段和有效规则可正常命中缓存。审核复用与锁等待路径也遵守相同约束。
4. 同名字段不会触发其他业务级联；提取与审核过滤结果一致。
5. 两条分类路径覆盖标准名称、别名、中台编码、未知材料及易混淆文件。
6. 同步、超时后任务查询及重复请求行为符合约定；跨业务/阶段复用任务 ID 不返回错误业务数据；错误从接口到任务及网关保持一致。
7. 对四场景构建 4×4 请求类型与核心材料内容的匹配矩阵，覆盖同场景成功及其余错业务/错阶段情况。历史参考材料另按兼容矩阵验证，不与核心材料混为一类。
8. 两个接口均覆盖“请求产权转让-预披露，实际企业增资文件”，分别断言错误码、期望类型、文件位置、识别依据、任务失败，且未执行后续提取/审核、未写入成功缓存。
9. 覆盖改名文件、错误中台编码、伪装 `file_type`、显式配置 ID、传入已确认字段、已有缓存、首份正确后续混入错误文件及合并 PDF，均不能绕过内容校验。
10. 通用材料配合正确核心材料可通过；仅通用材料、阶段无法判断、解析失败及 LLM 失败返回各自错误；允许的历史参考材料不被误拒绝。旧缓存无校验记录时重新校验。

对应回归重点：`tests/test_file_hash.py`、`tests/test_cache_policy.py`、`tests/test_task_store_cache.py`、`tests/modules/test_task_boundaries.py`、`tests/api/test_classification_async.py`、`tests/api/test_platform_gw.py`；新增四场景规则、内容识别、材料集合匹配、结构化错误、配置匹配及级联隔离用例。工程测试使用替身隔离外部服务；真实 OCR、LLM 和存储服务通过集成回放验证。

### 业务样本验收

- 建议四个新场景各先提供 5 个以上代表项目用于开发，验收扩展至每场景 10～20 个项目；必须包含正常、材料缺失、多来源冲突及多主体/表格样本。
- 另外准备跨业务、跨阶段、混合材料、通用材料、文件改名及模板含糊样本，单独统计错配检出率、正常材料误拒率和无法判断率。固定验收错配样本集应全部返回预期错误；真实推广效果通过样本持续评估，不承诺任意文件均能确定识别。
- 正常样本可完成“分类 → 提取 → 人工确认字段 → 审核 → 溯源”的闭环。
- 关键字段的正确性和审核通过/不通过/待确认，与业务确认的标准答案逐项比对。
- 金额币种及单位、比例、企业名称/统一社会信用代码、基准日期列为重点；缺失或冲突不能无依据生成值或判为通过。
- 溯源指向实际来源文件和内容，抽检页面/单元格定位；多文件、多页与重复主体重点检查。
- 字段准确率、审核一致率和处理耗时分别统计，阈值由 P0 根据业务风险及基线确认，不在样本不足时承诺数字。
- 四种现有实物业务通过基线回放，无新增关键错误；性能按同等文件规模与字段量比较。

## 6. 发布与回退

1. 备份当前代码版本及四套规则配置，保留可回放的基线结果。
2. 先部署能识别八种业务的代码、材料校验与结构化错误能力及新缓存命名空间，再部署四个新配置；未验收前保持禁用或不开放上游入口。
3. 发布校验器检查规则模型、字段引用、材料可解析性、级联引用，以及各业务启用配置数量。首期每个新类型只启用一套已验收配置。
4. 测试环境完成样本验收后，启用配置并开放上游入口，记录配置 ID、版本和规则指纹。
5. 观察业务失败、待确认比例、跨业务/阶段冲突、材料无法判断及误拒情况、缓存隔离和处理时长。材料校验不能在失败时默认放行，避免降级后绕过本次要求。
6. 业务配置问题先关闭对应新入口及配置；回退到仅支持四类枚举的旧代码前，须将四个新类型 JSON 从其读取目录中备份移出，避免旧模型解析新类型失败。旧任务保留，缓存按命名空间隔离；回退版本不支持的新错误字段不作为继续开放新入口的依据。

## 7. 启动前需要的输入

- 四个场景各自的字段编码与表单字典，以及同业务预披露/正式披露差异，含必填、类型、枚举、金额/比例/日期口径。
- 四场景材料清单、标准文件及中台材料编码，含同类多份文件的角色和年份区分方式；明确核心识别材料、通用材料及历史参考材料的兼容范围。
- 提取来源优先级，以及逐条审核要求、缺失处理、冲突处理和人工确认条件。
- 代表性真实或脱敏项目及标准答案，包含多股东、多转让方、历史财务数据等边界情况。
- 错业务、错阶段、混合上传和仅通用材料的样本，以及可核对的类别/阶段识别依据。
- 上游系统对四个新业务值、结构化错误码及提示信息的调用约定、表单字段与展示需求，及业务/测试验收负责人。

完成标准：四个新场景能够分别完成录入助审闭环；提取和审核均能识别并拒绝有明确证据的跨业务及不兼容阶段材料，对不确定情况返回明确错误；规则、错误提示与溯源通过验收，现有四类业务通过回归，部署和回退步骤可执行。
