# 需规分析与需求追踪矩阵

分析日期：2026年11月4日。需求依据为用户提供的《产权转让、企业增资、机动车.rtf》，正文已经 Windows RichTextBox 正确解码，保存在同目录 requirements.txt，共411行。章节编号沿用原材料，包括“一.3.2”后跳到“一.4.3”的情况。requirements.md 是 Pandoc 对代码页936错误解码的输出，不作为证据。

## 一 范围与来源结论

本次需规要求六个智能体场景：机动车有纸业务车辆任务单智能录入、机动车有纸业务智能助审、产权转让预披露辅助录入、产权转让正式披露辅助录入、企业增资预披露辅助录入、企业增资正式披露辅助录入。产权和增资的四种场景共用创建、状态、结果接口，通过业务类型和披露阶段选择独立配置与提示词。需规没有列出产权和增资的自动助审要求，不能把既有开发草案中产权和增资审核视为本次必交范围。

机动车分拍卖、解体业务；其材料集合及助审节点不同。原图由主代理提取并查看：解体与拍卖均有经办核实阶段的助审节点1及提交经理时的助审节点2，后续经理、交易审核部查看节点2结果。智能助审提供建议和证据，流程决策仍由业务系统的人工审核节点承担。产权和增资流程图中的三级审核为业务系统人工流程，不等于本期新增自动助审。

增资流程图中正式披露阶段绿色框误写为预披露辅助录入，与正文一.4.5.2冲突。设计以正文“企业增资正式披露项目辅助录入”为准，作为原材料勘误记录。

| NF-19 | 一.9应用层 | 密码≥8位且含至少三类字符；90天定期更换为建议；失败/超时退出；双因素且含密码技术 | 按统一身份平台实现并验收；区分需规强制项与90天建议项，不在业务微服务重复建设账号体系 |
| NF-20 | 一.9应用层 | 审计覆盖每用户、记录时间用户类型成功与否、保护进程、定期备份 | 任务创建、查询、取消、重触发、文件证据访问和规则发布均留审计事件 |
| NF-21 | 一.9应用层 | 涉法律认定场景宜不可否认，外部通信非对称加密 | 确认需签名的场景与数据格式；来源证据、规则和结果摘要可供完整性校验 |
| NF-22 | 一.9应用层 | 输入合法性、避免注入、抵抗提示词注入 | 附件视为不可信数据，不将文内指令执行为系统指令；结构化输出校验和证据核对，数据访问仍由服务授权 |

## 四 材料目录与必交性边界

### 机动车录入材料角色

| 角色 | 需规原材料名称或别名 | 处理要求 |
| --- | --- | --- |
| 处置授权或申请材料 | 车辆处置申请表／中央行政事业单位国有资产处置委托书／行政事业单位国有资产处置申请表／委托函 | 依据转让方类型确认可替代关系，不能把四个名称全部当必交 |
| 处置清单 | 车辆处置明细表／处置清单 | 车辆基准清单候选，最终以业务规则确认为准 |
| 内部决策 | 内部决策 | 具体文件形式和必交条件待确认 |
| 批复文件 | 批复文件 | 批复文件类型通过内容识别；按主体和处置方式配置条件 |
| 主体资格 | 营业执照／事业单位法人证书 | 按主体类型替代；通用材料不承载独立业务类别判断 |
| 行驶证 | 机动车行驶证 | 可含多车多页；提取车牌及注册日期等指定信息 |
| 登记证 | 机动车登记证书 | 同“机动车登记证”；映射登记日期等同义字段 |

需规使用“应上传附件包括”，同时在数量统计中另提“必传文件”，没有提供逐材料、逐处置方式的必交条件矩阵。因此设计可给出角色配置模型，但必须将正式必交策略标为上线前业务确认项，不能臆造七组全必交或任意指定数量基准。

上述清单是支持覆盖范围，不等于每次助审均要求全部上传。必交与参考材料由处置方式、助审节点及具体规则配置。

## 六 范围冲突处理建议

已有《产权与增资业务扩展开发计划》将四场景字段审核、文件审核、溯源纳入扩展，而本次需规只列产权增资辅助录入。概要设计应保留共享审核能力的扩展接口，但基线交付范围以本次需规为准。若业务继续要求产权增资助审，应单列后续变更范围并补充审核要点，不由设计文档隐式扩大。

对“平均响应时间小于3秒”的原指标应原样保留，同时给出受理/查询与后台处理分别测量的设计建议，并在待确认表里解决合同计时边界，不能通过改写指标掩盖长耗时模型调用。

对车牌两两校验，应保留业务要求的比较覆盖，同时在多车批次中先按车辆及材料作用域建立比较关系。车辆A和车辆B本来不同号牌，不应仅因二者不同而产生跨文件不一致。批次清单类文件比较集合，单车证照比较所属车辆；缺少稳定归属的附件显式待确认。
