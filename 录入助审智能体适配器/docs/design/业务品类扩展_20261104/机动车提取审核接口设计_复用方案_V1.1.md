# 机动车提取与审核接口设计

版本 V1.1 复用方案评审稿

日期 2026年11月6日

本方案保留现有 POST /api/v1/extraction/sync、POST /api/v1/audit/sync 及任务查询、取消接口，扩展机动车请求和结果。相较V1.0中独立的 /vehicle 接口族，本方案将“复用现有入口和任务类型”作为推荐方案。本文是接口设计，尚未修改业务代码或发布接口。

## 1 接口和处理边界

| 功能 | 方法和路径 | 任务类型 |
| --- | --- | --- |
| 车辆批量提取 | POST /api/v1/extraction/sync | extraction |
| 车辆批量审核 | POST /api/v1/audit/sync | audit |
| 状态查询 | GET /api/v1/task/{task_id}?type=extraction或audit&include_details=false | 原任务类型 |
| 结果查询 | GET /api/v1/task/{task_id}?type=extraction或audit&include_details=true | 原任务类型 |
| 取消任务 | POST /api/v1/task/{task_id}/cancel?type=extraction或audit | 原任务类型 |

原生响应继续使用code、message、trace_id、timestamp、data外壳，成功code为数值200。平台适配维持原生Body和现有业务头规则，按平台前缀与任务query路径接入。机动车无需新增vehicle_extraction或vehicle_audit任务类型。

提取负责材料匹配、公共字段、逐车字段、数量及号牌一致性和证据；审核负责检查人工确认后的公共及逐车字段、归并经办与机构材料、执行指定节点规则并给出四态结果。提取冲突提示不能直接替代审核结论。

## 2 公共请求约定

| 字段 | 类型 | 机动车约束 |
| --- | --- | --- |
| request_id | string | 必填。调用方作用域内的幂等标识；重试沿用，变更输入换新值 |
| project_id | string | 新增，必填。业务项目或授权空间，服务端校验调用主体的访问权限 |
| extraction_type或audit_type | string | 必填，新增值为机动车-有纸 |
| disposal_mode | enum | 新增，必填。auction拍卖，dismantling解体 |
| rule_config_id | string或null | 沿用，可选。未传按业务、处置方式及审核节点选已发布规则 |
| timeout | integer | 沿用，毫秒，默认1000，最小1000；只是同步等待窗口 |
| task_id | string或null | 兼容原模型。机动车新建不传，重试优先request_id；不得用此字段覆盖另一输入 |
| files | array | 本轮完整材料清单，非空；每份文件独立标识，不按名称去重 |

VehicleFileInput在原文件输入上增加以下字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| file_id | string | 必填，稳定的材料版本标识；内容变化应使用新ID |
| file_url | string | 沿用，必填；下载时校验访问范围、大小和实际内容 |
| file_name | string | 沿用，必填；展示名，不能作为唯一身份 |
| file_type | string | 沿用，必填；扩展材料枚举，声明值不能替代正文识别 |
| uploader_role | enum | 新增，必填；operator经办，agency服务机构，由可信上传元数据核验 |
| entity_ids | array<string>或null | 新增，可选；已知的车辆归属线索。未填写可由系统识别，不要求调用方提前拆分合并PDF |
| file_content_hash | string或null | 沿用可选MD5，服务端核验；服务端计算独立可信内容指纹 |
| file_size | integer或null | 沿用可选，字节 |

拟新增的vehicle_disposal_list、vehicle_driving_license、vehicle_registration_certificate等是内部材料编码，需同步注册枚举、材料中文标签、分类提示词、规则和中台映射。现有vehicle_certificate只是合并父类，不能用它判断行驶证与登记证均已齐全。

entity_ids不具备授权作用，也不保证声明归属正确。多车辆PDF保持一个file_id，通过页和识别记录对应不同entity_id。批次共用材料可以不指定entity_ids，其适用范围由材料规则判断。

## 3 提取接口

### 3.1 请求示例

以下为结构样例，示例未列出全部业务材料，生产必交清单按已确认的场景规则执行。

```json
{
  "request_id": "vehicle-extract-001",
  "project_id": "project-001",
  "extraction_type": "机动车-有纸",
  "disposal_mode": "auction",
  "timeout": 1000,
  "files": [
    {
      "file_id": "file-list-001",
      "file_url": "https://example.invalid/files/list.pdf",
      "file_name": "车辆处置清单.pdf",
      "file_type": "vehicle_disposal_list",
      "uploader_role": "operator"
    },
    {
      "file_id": "file-license-001",
      "file_url": "https://example.invalid/files/licenses.pdf",
      "file_name": "行驶证合并.pdf",
      "file_type": "vehicle_driving_license",
      "uploader_role": "operator"
    }
  ]
}
```

数量基准材料和字段来源优先级从发布规则读取，不由每次请求随意指定。多份基准不一致或存在未识别车辆时返回待确认及对应来源，不擅自选一个总数。

### 3.2 结果模型

在现有ExtractionData增加可选vehicle_data，只有机动车分支返回。原有results字段对机动车固定为空，全部机动车公共字段和逐车字段放在vehicle_data，避免一份值在多个位置出现；原实物results含义不变。

| vehicle_data字段 | 类型 | 语义 |
| --- | --- | --- |
| schema_version | string | 初始1.0，表示车类扩展对象版本 |
| common_fields | array<VehicleField> | 一次处置任务共用的转让方、地址、审批单位等 |
| vehicles | array<VehicleExtractionItem> | 每条基准车辆记录一个实体，包含未识别号牌记录 |
| material_match | object | 附件匹配项、缺失材料、错误类型及未识别材料 |
| vehicle_statistics | object | 原始行数、已识别数、去重号牌数及未知/重复统计 |
| cross_file_checks | array | 按适用范围比对材料中的车辆集合或单车信息 |
| warnings | array | 可继续处理但需人工复核的问题 |

VehicleExtractionItem为entity_id、plate_number、identity_status、fields。entity_id由首次提取分配并在本次处置中稳定使用；号牌更正不改变entity_id。号牌缺失时plate_number=null，identity_status=missing，仍保留原记录和证据。

VehicleField定义如下：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| field_code field_name | string | 稳定编码及展示名称；正式编码由字段表冻结 |
| value_type | enum | text date decimal boolean single_choice multiple_choice等 |
| value | JSON值或null | 推荐回填值；日期ISO形式，金额十进制字符串并带unit |
| field_status | enum | success pending failed |
| selected_source_file_id | string或null | 选中来源，来源冲突仍保留其他候选 |
| selection_reason | string或null | 规则优先级等选值原因 |
| consistency | enum或null | consistent inconsistent undetermined |
| sources | array<VehicleSource> | 各来源提取值及证据，按规则优先级排列 |
| reason_code reason | string或null | 待确认或失败原因 |

VehicleSource含file_id、file_name、extracted_value、page_number、source_content、priority、preview_image_url及可选regions。page_number从1开始；regions以PDF点坐标bbox及标准页尺寸声明坐标系和旋转，不能混用像素。Word来源增加原段落/单元格锚点及转换PDF映射。缺失材料通过reason列规则期待的材料名称，不能伪造一份源文件。来源链接必须按项目授权。

## 4 审核接口

### 4.1 请求约定

沿用AuditRequest.audit_type、confirmed_fields、files、rule_config_id、request_id、timeout和trigger_type。新增project_id、disposal_mode、extraction_task_id及vehicle_data。

| 字段 | 机动车含义 |
| --- | --- |
| audit_type | 固定机动车-有纸 |
| trigger_type | node_1机构提交后经办核实；node_2补充后续信息并提交经理时 |
| confirmed_fields | 本轮人工确认的公共字段，沿用ConfirmedField结构 |
| vehicle_data.vehicles[].entity_id | 与提取结果对应的稳定车辆身份；手工录入可用业务系统稳定ID |
| vehicle_data.vehicles[].confirmed_fields | 本轮该车人工确认字段，不直接拿提取建议替代 |
| extraction_task_id | 可选关联，仅用于身份及来源追踪，不自动复制旧字段或旧附件为本轮输入 |
| previous_task_id | 可选，链接上轮审核；重审创建新任务，不覆盖旧结果 |
| business_revision | 可选，建议传业务单据版本，用于前端识别审核结果是否过期 |

机动车允许公共confirmed_fields为空，但vehicles须非空且每车有确认字段；原实物仍保留原校验。这里需要调整现有min_items=1验证，不能只向旧模型增加一个嵌套字段。

files是本轮完整材料清单，包括参与审核的经办材料和机构材料；不自动把未传的旧附件加入审核。相同file_id只能出现一次；文件名相同但内容不同应使用不同file_id。服务端按来源角色和归并规则计算有效材料，返回归并决策，不删除原件。

### 4.3 审核结果

在AuditData增加可选vehicle_data。机动车时原audit_results固定为空，公共和逐车结果均放在vehicle_data；summary统计本轮全部公共与逐车原子规则。

| vehicle_data字段 | 类型 | 说明 |
| --- | --- | --- |
| schema_version | string | 车类扩展对象版本 |
| common_audit_results | array | 公共字段及任务范围的规则 |
| vehicles | array | entity_id、plate_number、audit_results |
| material_merge | object | 有效材料、替代记录、冲突；双方原件均可追踪 |
| cross_file_checks | array | 号牌及材料集合差异 |

VehicleAuditRuleResult含audit_rule_id、audit_rule_name、audit_result、audit_explanation、related_fields、sources及可选reason_code。related_fields需包含待审值和从指定来源提取的值；数量、金额规则应包含单位和比较表达式。

响应为关键业务字段示例，生产实现还返回原AuditData要求的confirmed_fields、processing_time_ms等通用字段。示例规则用于解释结构，不代表已确认的完整审核要点。日期规则假设其参考集合只要求行驶证且证据齐备；登记证缺失影响另一项规则。如同一规则同时要求行驶证和登记证，缺失时应按该规则完整性政策输出待确认，不能套用示例直接判失败。

四态为passed、failed、pending、not_applicable。not_applicable仅用于规则明确不适用，不替代原manual_review；旧业务仍按原枚举口径。机动车summary.total=passed+failed+pending+not_applicable。任务completed意味着处理结束，可同时包含业务failed和pending，不返回HTTP500表示业务不通过。

## 5 同步等待与任务查询

提取沿用现有pending占位响应，带task_id、extraction_type、空results及通用统计。审核沿用processing占位语义；任务生命周期在查询中仍使用pending/processing/completed/failed/timeout/cancelled。

请求等待超过timeout时后台继续执行，不能将等待超时标为执行失败。客户端随后调用：

```text
GET /api/v1/task/extract-001?type=extraction&include_details=false
GET /api/v1/task/extract-001?type=extraction&include_details=true
GET /api/v1/task/audit-001?type=audit&include_details=true
```

完成后的data.result为原ExtractionData或AuditData，其中包含vehicle_data。先根据查询data.status判断是否继续轮询，再读取data.result中的业务结果；不能将result.status=pending（字段待确认）误当成任务仍在运行。

如果需在提取完成前展示附件匹配，任务状态增加可选material_match_snapshot，包含ready与已识别/缺失项；include_details=true时返回最新匹配快照。由同一任务持久化阶段结果，不另建车辆状态系统。

大批量结果扩展现有任务查询的可选result_cursor和page_size参数：只对机动车生效，以固定task_id和结果指纹绑定游标，page_size建议默认20、上限100，实际值按平台载荷和压测发布；只分页vehicle_data.vehicles，公共字段和全任务汇总不按页重算。旧调用不带参数保持原行为，图片/PDF采用授权引用。

## 6 幂等 规则与缓存

先按调用方和request_id查询幂等记录，同一规范化原始请求返回原task_id及其固定规则快照；同ID不同参数返回409 IDEMPOTENCY_CONFLICT。只有首次请求选择当前默认规则，后续默认配置发布不影响该任务。当前代码需要将查重、新建和状态重置行为改为原子处理，不能认为已经严格幂等。

每个任务固定业务、处置模式、节点、材料版本和规则快照。审核缓存还包含本轮公共/逐车确认值；不能仅按文件内容复用上次审核。人工改值、增删车辆、补传附件、变更节点都需新request_id。重新审核创建新task_id并关联previous_task_id，不重置旧结果。

多车提取和审核始终按entity_id保存字段及多来源数组，不能沿用“只展开数组第一条”或“field_name+file_type对应单值”的索引。多车同类型材料可共享解析，但不能把不同车辆数据合为一个字段值。

## 7 错误和部分结果

| 情况 | 处理 |
| --- | --- |
| 参数不合法 配置不存在或场景不匹配 | 沿用HTTP400或404及结构化error |
| request_id重用但输入变化 | HTTP409 IDEMPOTENCY_CONFLICT |
| 项目/文件无权访问 | 拒绝；不可见任务统一404避免枚举 |
| 某辆车缺材料或字段无法识别 | 保留该车，字段或相关规则pending，整体可partial/completed |
| 多来源冲突、归并关系无法确认 | 返回冲突及证据，受影响项pending |
| 任务整体下载/解析/模型服务失败无法继续 | 生命周期failed，保存可重试标识和文件详情 |
| 查询失败任务 | 查询HTTP200，data.status=failed，data.error为原结构化错误 |
| 审核规则判不通过 | HTTP200，业务audit_result=failed |

扩展ErrorDetail支持file_id、entity_id、page_number、reason_code等可选字段，并在异常处理器、TaskStore和网关完整透传；不得只拼入error_message字符串。

## 8 拆页与实现清单

按页拆分是用户独立触发的文件操作，不默认放进每次提取或审核。可补通用POST /api/v1/file/split，引用提取任务、所选PDF和车辆范围，返回子任务；其接口细节另行定义，不需要为此新增整套机动车提取/审核入口。

实施需改动：业务枚举与材料注册；ExtractionRequest/AuditRequest可选扩展及条件校验；ExtractionData/AuditData.vehicle_data；机动车规则选择和两节点策略；实体级提取/确认/审核索引；材料归并与图像审核；任务阶段快照、分页与结构化错误；业务隔离缓存和严格幂等；平台映射及旧实物回归。原生response_model必须包含新增对象，不能仅在服务返回字典中增加字段。

验证重点为：两车同字段不覆盖、缺号牌保留记录、单车证照不被当整批缺失、人工更正后审核使用新值、同请求重试不重复创建、两节点不串规则、机构归并可追溯、四态统计一致，以及旧四类实物契约不变。

## 9 与现有代码和需规的关系

现有入口见src/api/v1/endpoints/extraction.py和audit.py；现有请求与响应见src/schemas/extraction.py、audit.py；任务查询见src/api/v1/endpoints/task.py。当前已有extraction/audit/classification三种TaskType，本方案提取与审核继续使用前两种。

需规一.3.1.3.1要求一份公共信息及多条车辆信息；一.3.1.2.5要求数量和号牌跨文件统计；一.3.1.3.2要求用户触发按页拆分；一.3.2.1.1要求两阶段附件归并；一.4.3.4.5要求四态审核。具体字段、材料必交条件、归并判定条件和节点审核范围，仍以正式业务字段表及审核要点冻结。
