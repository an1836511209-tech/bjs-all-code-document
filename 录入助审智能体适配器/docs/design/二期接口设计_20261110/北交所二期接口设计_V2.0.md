
## 1  文档说明


### 1.1  本次修订做了什么

V2.0 是**「复用版」**。评审确认了两条原则：①凡一期能覆盖的能力，一律复用一期接口与报文结构，不新增；②确实覆盖不了的，才加入参/出参，且新增项全部可选、默认不影响一期调用方。

按这两条原则，V1.1 中的以下二期专有结构全部取消：`disclosure_data`、`context`、`precondition`、`applicable`、`required`/`fill_mode`、`counts`、`business_type_check` 对象、请求侧 `file_id`、`entity_plates`、`include_evidence`、`pagination`、`warnings`。

本版的主要工作：

- **产权增资**：直接采用已对齐的版本（5 个接口、0 处新增入参/出参），只补「结果如何归组回中台接口」一节；
- **机动车**：整章重新设计——7 项能力里 6 项复用一期，只新增 1 个接口、7 处可选字段；
- 字段字典：正文不再重复 469 行字段表，全量见《字段字典_产权转让企业增资.xlsx》与《字段字典_机动车.xlsx》，正文只保留决定接口形态的两张「公共 / 逐车归属表」。

## 2  设计原则与改动总览


### 2.1  判定规则：什么算「复用得了」

对每项能力先问三个问题，三个都能过就不动一期协议：

1. **一期接口的入参够不够？** 不够 → 加可选入参；够 → 复用。
2. **一期接口的出参能不能承载结果？** 能 → 复用；不能 → 加可选出参或新接口。
3. **加了会不会影响一期调用方？** 可选字段 + 默认值不改变一期行为 → 可接受；改必填/改结构 → 不接受。

### 3.4  审核结论

一期枚举是 passed / failed / pending / manual_review。需规的第四类是「无需审核」（机动车 57 个审核字段中 22 个、20 个中 6 个属于此类），一期没有对应值，因此**新增 1 个枚举值** not_required。

**表 3-4  audit_result 枚举**

| 取值 | 业务含义 | 前端处理 |
|---|---|---|
| passed | 通过 | 打勾，不展示说明 |
| failed | 不通过 | 展示说明 + 溯源，退回修改 |
| pending | 待确认（材料缺失 / 无法判断） | 提示补材料或人工确认后放行 |
| not_required | **新增**：无需审核 | 默认折叠，但必须返回（用于统计人工审核率） |
| manual_review | 需人工审核（一期存量，二期机动车不使用） | — |

### 4.5  业务类型一致性校验

提取前解析申请书封面文种，与 extraction_type 比对。不一致时中止，**两种呈现取决于判定时机**：

**表 4-10  文种不一致的两种呈现**

| 时机 | 调用方看到 | 任务状态 |
|---|---|---|
| 同步等待窗口内判定完成 | HTTP 400，error_code=HTTP_ERROR，error_message 给原因 | 服务层先把任务标 failed 再抛错，所以 400 之后再查任务是 failed，不是 404 |
| 窗口已超时、任务转后台后才判定 | 先返回 pending + task_id；轮询后 status=failed | error_message 说明原因 |

> **注意**：前端不要把 400 当作「任务没建」。两种情况下任务都会被标记 failed，查询接口始终可查到该 task_id。

### 4.7  结果如何归组回中台接口

`results[].field_name` 是**规则分组码**（如 MAIN、ZRF、GQJG、SJBG），不是中台字段码。归组依据是 `extraction_rule.platform_interface`。12 个分组的对应关系如下（可从现有规则配置直接导出）：

## 5  机动车智能录入与智能助审接口


### 5.1  设计要点：7 项能力里 6 项复用一期

机动车与前两个品类的本质差异有四条：多份文件、多辆车、按车牌聚合多来源、两个阶段。前三条都会冲击一期「一个字段=一个值」的假设，但**不是每条都需要改协议**。逐条判定：

**表 5-1  差异判定**

| # | 差异 | 一期能不能承载 | 结论 |
|---|---|---|---|
| 1 | 一次任务多份文件 | files 本来就是数组 | 复用，不改 |
| 2 | 同一字段多来源 | values[] 本来就是多来源数组 | 复用，不改 |
| 3 | 多辆车，字段要归属到车 | **不行**：field_id 是规则 ID，N 辆车会有 N 条相同 field_id，无法区分 | 加 1 个可选出参 results[].vehicle |
| 4 | 附件类型匹配 / 缺失 / 车辆数量统计 / 车牌一致性 | **不行**：这些不是「字段」，results 装不下 | 加 1 个可选出参 data.vehicle_data |
| 5 | 经办与机构材料归并（助审） | **不行**：一期不区分上传方 | 加 1 个可选入参 files[].uploader_role |
| 6 | 按车提交确认值 / 按车返回结论 | **不行**：confirmed_fields、audit_results 都是扁平数组 | 各加 1 个可选字段 vehicle |
| 7 | 「无需审核」第四态 | **不行**：一期只有 passed/failed/pending/manual_review | 加 1 个枚举值 not_required |

结论：机动车需要 **1 个新接口 + 1 个可选入参 + 5 处可选字段/枚举**，其余全部复用一期。原 V1.1 的 context、entity_plates、pagination、warnings、schema_version、4 个专用视图片接口全部取消。


### 5.2  为什么必须给 results 加 vehicle

一期的 `field_id` 取规则 ID。机动车「审批原值」这条规则对 3 辆车会产出 3 条结果，field_id 完全相同，业务后端无法判断哪条属于哪辆车，也无法把「第 2 辆车」的结果挑出来。所以必须给每条逐车结果一个属主：

```json
{
  "field_id": "VEH_ENTRY:SPYZ",
  "field_name": "SPYZ",
  "field_type": "number",
  "field_status": "success",
  "vehicle": {
    "vehicle_id": "veh_0002",
    "plate_number": "京B67890",
    "plate_number_normalized": "京B67890"
  },
  "values": []
}
```

公共字段（转让方、审批单位、任务单信息等）不出现 vehicle 字段，或为 null——业务后端按「有 vehicle 就归该车，没有就是任务级」处理，与一期的用法完全兼容。

#### 5.3.4  按车牌聚合的规则

这一节是业务后端最需要理解的，也是机动车与前两个品类最大的不同：

**表 5-8  按车牌聚合规则**

| 规则 | 说明 |
|---|---|
| 聚合键 | plate_number_normalized。归一：全角转半角、去空格与「·」「-」「.」、字母大写 |
| 跨文件合并 | 同一车牌在多份文件出现时，不是取一个值，而是全部进 values[]，按录入优先级排序 |
| 选值 | 按 P1→P2→P3→P4 取第一个成功的来源作为首选；行驶证/登记证只参与一致性校验，不参与选值 |
| 一致性 | 各来源归一值相同 → 一致；不同 → field_status=pending、inconsistent_values 记差异值 |
| 一号牌多行 | 基准清单同一车牌出现多次 → identity_status=duplicate_plate，两行都保留 |
| 无车牌记录 | 整条进 unidentified_vehicles，字段照常提取，用 seq 定位清单第 N 行 |
| 清单外车辆 | 材料中出现但基准没有 → identity_status=extra，不丢弃 |
| 多车合并 PDF | **不要求调用方拆分**，服务端按页识别并归到对应车牌 |

> **注意**：同一车牌在两张材料里写法不一致（如「京A1234」与「京A12345」）会被归一成两个车牌、当成两辆车。这类情况只能靠 vehicle_statistics.material_vehicle_counts 的数量差异暴露，需人工确认。

判定「同一份材料的两版」需同时满足：①file_type 相同；②文件名归一（去扩展名、去「副本」「最终版」等后缀、去空白）后相同；③按车辆归属的材料，识别出的车牌集合有交集。任一不满足即视为不同材料，两份都纳入、形成多来源。

**表 5-13  归并的四种情形**

| 情形 | 举例 | 处理结果 |
|---|---|---|
| 同名同类型 | 经办「行驶证.pdf」+ 机构「行驶证.pdf」 | 只保留机构版参与判定，经办版进 replacements（reason=higher_priority_role）；hash 相同则 reason=same_hash |
| 同类型不同名 | 经办「行驶证合并.pdf」（两车）+ 机构「行驶证-京A12345.pdf」 | 三份全部纳入，对京A12345 形成两个合法来源，按 or/and/priority 判定 |
| 同名但内容不一致 | 机构版注册日期 2018-06-02、经办版 2018-06-01 | 按机构版出结论，**同时把差异写进 audit_explanation**，不能静默丢弃经办版 |
| 无法判定归属 | 两份都是多车合并件但车牌集合对不上 | 进 conflicts[]，相关审核项一律 pending，交人工 |

| **字段审核** | 系统字段值 vs 材料中的值（逐车） | 一条规则一条 `audit_results`，带 `vehicle` |
| **文件审核** | 材料本身：车牌跨文件是否一致、图片里是不是机动车、文件是否有效齐备 | 一条规则一条 `audit_results`，**不带 `vehicle`**，结论在 `audit_point_details[]` |

文件审核**完全复用一期能力**（`AuditType.FILE_AUDIT` 与 `AuditRuleResult` 的 `file_type` / `audit_points` / `audit_point_details` / `uploaded_files`），本版**零协议改动**，只是把机动车的审核规则配进去。

报文侧要点：

- 文件审核的 `audit_result`、`audit_explanation`、`confidence` 在**规则层为 null**，真实结论在 `audit_point_details[]`，前端要按要点逐条渲染；
- `audit_points` 是该规则的要点原文（可含多个编号要点），`uploaded_files[]` 列出该规则涉及且已上传的材料；
- 文件审核**不出现 `vehicle`**：它判的是「这几份文件的号牌是否一致」，结论天然是跨车的，不能挂到某辆车；
- 一致性不通过时，涉及的车牌与文件列表写在 `audit_explanation` / `audit_point_details[].audit_explanation` 里，结构化明细仍可由提取结果 `vehicle_data.plate_consistency` 取到（见下）。

> **说明**：录入与助审对车牌一致性的分工是——**录入侧**（`/extraction/sync`）在 `vehicle_data.plate_consistency` 里给出「哪些文件的号牌与基准不一致」的结构化结果，供经办当场发现并修正；**助审侧**（`/audit/sync`）用文件审核给出四态结论，进入审核统计与人工流程。两者同一套判定，只是出口不同，助审的 `vehicle_data` 里不再重复放 `plate_consistency`。

三个容易踩的点：

1. **文件审核的规则层 `audit_result` 一定是 null**。前端如果只读 `audit_results[].audit_result` 上色，这两条会显示成「未审核」；必须按 `audit_type` 分支，文件审核下钻到 `audit_point_details[]`。

### 5.6  任务查询与取消

完全复用 4.6 的两个接口，机动车无差异。`total_count` 在提取任务里 = 公共字段数 + Σ 每车字段数；审核任务里 = 本轮规则数；分类任务里 = 文件数。前端算进度时按任务类型取分母。

轮询建议：前 30 秒每 2 秒一次 `include_details=false`；之后每 5 秒一次；完成后再取一次 `true`。


### 5.7  多页附件按车牌拆分：本期不建接口

需求规格书 3.1.3.2 要求支持「一个 PDF 内含多辆车证照」按页拆分并按车牌重命名。本版的处理方式：

- **识别阶段已按页归属**：服务端内部分页识别车牌，每页结果归到对应车辆，调用方无需预先拆分；
- **物理拆分是归档需求**：仅在业务需要把单车证照单独存一份附件时才有意义，与录入/助审的判定无关；
- 因此本期不建接口，列为 P2 待确认项（表 8-1 第 9 条）。若确认要做，再追加 `POST /api/v1/file/split-by-plate`，入参 {task_id, file_id, plate_numbers[], naming_rule}，出参 {files[{plate_number, file_url, page_range}]}。

## 6  联调注意


### 6.1  任务状态与业务结论是两层

`data.status`（pending/processing/completed/failed/timeout/cancelled）是任务生命周期；`data.result.status`（success/partial/pending/failed）是提取业务结论。任务 completed 只表示处理结束，业务可能仍有 pending 字段，需转人工复核。


### 6.2  缓存

一期缓存索引 `cache:hash:{files_hash}` 只由文件 `file_content_hash` 的排序集合计算，**不含业务类型与规则版本**。产权增资因 `is_disclosure` 分支不启用缓存（`from_cache` 恒 false）；机动车启用。

> **注意**：二期 6 个业务类型并存后，同一批文件理论上可能命中别的品类的缓存。建议把「业务类型 + 规则版本 + 文件哈希」一起纳入缓存键——命中率会下降，但能避免用 A 品类的规则结果回答 B 品类请求。这是**一期代码改动**，需单独评估，不属本接口设计范围。


### 6.3  「条件不适用」的处理

一期用级联（CONDITIONAL）在主字段值的基础上决定提哪些子字段，未触发的子字段记为 `field_status=failed` + `error_message` 以「级联未触发」开头，且 `failed_count` 已排除。

**业务后端必须按前缀过滤，不得把这些项计为提取失败**，也不回填。产权增资 87 个带前置条件的字段都走这条路径。（长期建议：给 `field_status` 增加 `not_applicable`，用枚举而不是中文前缀表达状态。）


### 6.4  错误码分层

本文档描述的是原生 API 层：参数校验失败 → 400 VALIDATION_ERROR（带 details）；业务异常 → 400/404 HTTP_ERROR；未处理异常 → 500 INTERNAL_ERROR；错误响应**不带 trace_id**，成功响应带。经北交所 API 统一管控平台访问时，上述码会被映射为 PV-001 / PA-00x / PI-00x，以平台文档为准。


### 6.5  溯源与预览图

`preview_image_url` 可能是相对路径，需按服务地址拼接；访问需携带与请求相同的鉴权，且只能访问本项目的文件，越权统一 404。过期后返回空串，此时用 `source_content` 文本兜底。


## 7  业务后端常见问题

**表 7-1  常见问题**

| # | 问题 | 答复 |
|---|---|---|
| Q1 | 机动车结果里 results 是空的吗？ | **不是**。本版把逐车字段放在 results 里，用 `vehicle` 标明归属；只有「材料匹配 / 数量统计 / 车牌一致性」这类非字段信息进 vehicle_data。与 V1.1 不同——V1.1 让 results 恒为空，本版不再这样。 |
| Q2 | 同一辆车多个字段、同一个字段多辆车，怎么区分？ | 看 `results[].vehicle.plate_number_normalized`。公共字段没有 vehicle。field_id 会重复，**不要用 field_id 做唯一键**。 |
| Q3 | 一个 PDF 里 5 辆车的行驶证，要我先拆吗？ | 不用。服务端按页识别车牌并归到对应车辆；文件在 material_match 里仍是 1 条。 |
| Q4 | 车牌写法不一致（京A·12345 / 京A12345 / 京Ａ12345）怎么对齐？ | 用 `plate_number_normalized` 做匹配键；`plate_number` 只用于展示。 |
| Q5 | 有辆车车牌没识别出来，结果里还有吗？ | 有，进 `unidentified_vehicles`，`identity_status=missing_plate`，字段照常提取，用 `seq` 定位清单第几行。 |
| Q6 | 清单 10 行、行驶证只有 8 份，缺的 2 辆怎么表示？ | 这 2 辆仍在 vehicles 里，依赖行驶证的字段 pending，并在该车的 `missing_materials` 里列明缺哪种材料。 |
| Q7 | 材料里出现清单外的车，返回吗？ | 返回，`identity_status=extra`，并在 vehicle_statistics 计数，不丢弃。 |
| Q8 | 车辆数量以哪份材料为准？ | 看 `vehicle_statistics.baseline_source`（通常是处置明细表）；各材料数量差异在 `material_vehicle_counts` 里并列，由人工判断。 |
| Q9 | 审批原值公共与逐车都有，以哪个为准？ | 以逐车为准回填；公共的合计值用于交叉校验，不一致时两处都会 pending。 |
| Q10 | 助审要传全量字段还是只传变更？ | 传本轮需要审核的全部字段。只审显式提交的字段，未提交的不审也不返回。 |
| Q11 | 审核不通过为什么 HTTP 还是 200？ | 审核结论是业务结果，不是接口错误。只看 `audit_result`。 |
| Q12 | pending 和 failed 怎么区分处理？ | failed=明确不符合，退回修改；pending=材料缺失/无法判断，补材料或人工确认放行。 |
| Q13 | not_required 的字段还要不要给我？ | 要。业务指标要统计人工审核率，前端也需要知道哪些被规则豁免。 |
| Q14 | 重新审核怎么传？ | 换新 request_id，带上更新后的 confirmed_fields 与材料；重审创建新任务，不覆盖旧结果。 |
| Q15 | timeout 1000ms 是不是太短？ | 它是同步等待窗口，不是任务时限。超时会返回 task_id，拿 task_id 去轮询，**不要重试整个请求**。 |
| Q16 | 重试会不会跑两遍？ | 复用同一个 request_id 就不会：同 request_id + 同内容返回首次任务；换了 request_id 才会真跑。 |
| Q17 | 200 辆车会不会超报文？ | 机动车结果可能较大。轮询用 include_details=false 只取状态；取结果后再按 vehicle 过滤展示。若单响应仍超平台 10MB，需要平台侧调大或分批提交材料。 |
| Q18 | 为什么产权增资没有 vehicle_data、没有 context？ | 产权增资一张申请书、一个项目，没有多车聚合问题；反显与默认值由中台自己做，AI 只负责从申请书提取，所以不需要 context。 |
| Q19 | 「级联未触发」的字段怎么处理？ | 不计失败、不回填，直接跳过（见 6.3）。 |
| Q20 | 机动车有没有文件审核？ | 有，而且是一期的原生能力（`audit_type=文件审核`）。机动车的文件审核包括①车牌跨文件一致性（底表 11 类文件合成一条规则）②图片内容是否为机动车及号牌比对 ③文件有效性（盖章/页数/有效期）。报文里与字段审核同处 `audit_results[]`，区别是**不带 vehicle**、规则层 `audit_result` 为 null、结论在 `audit_point_details[]` 里。见 5.5.5。 |
