# 概设接口审查（更正）

审查对象：《北交所人工智能中台二期项目概要设计说明书 v1》4.7.2 产权增资、4.7.3 机动车、4.7.4 归属与聚合。

口径：接口设计是否合理，现有录入助审项目能否二开实现。二期与当前代码不完全一致是预期，不把「代码里还没有」当成设计问题。

## 结论

合理，而且能做。产权复用提取、任务查询、取消。机动车复用提取和审核，用可选字段表达逐车结果，另加一个材料齐备度查询。这些都落在现有的解析、规则、任务链路上。

三套 status、智能体路径与管控平台 query 的差别，不作为设计问题。一期已经按这套结构在调用。

## 设计上建议收口的地方

1. 产权的质量检测和分类不要写成必调。质量检测不接收 Word，分类只有 `info_disclosure_application`，区分不了四类披露。需规要的是创建、状态、结果。这两项标成可选。
2. 业务类型不一致只保留一种返回。概设正文是任务失败，示例又是同步 400，标题还写成文件类型错误。建议只保留任务查询 `status=failed`。
3. 车牌一致性不要放三份。录入放在 `vehicle_data.plate_consistency`，助审放在文件审核要点里。助审的 `vehicle_data` 再放一份是冗余。
4. 材料齐备度查询本身合理。`GET /api/v1/vehicle/{task_id}/materials` 解决的是提取完成前任务结果仍为空。完成后 `vehicle_data.material_match` 又有一份，概设要写明未完成查前者、完成后读后者。`vehicle_data` 是对象，表头不要写成数组元素。

## 现有项目如何接住

| 能力 | 怎么做 |
|---|---|
| 产权四类提取、封面比对 | 披露类型和封面校验已经在提取任务里，补规则和字段映射 |
| 机动车逐车、上传方、无需审核 | 在现有提取、审核模型上加可选字段，一期实物调用不带这些字段 |
| 22 种材料、齐备度查询 | 扩展文件类型，用任务上已有的进度存匹配结果，加一个只读查询 |
| 按车牌归组 | 解析已有页码，在提取结果上归组。概设不提供拆分文件下载，与此相符 |
| 看图审核机动车和号牌 | 结论可以放进现有文件审核要点。当前审核读解析文本，看图需要新增识别，不必新接口 |

助审的 `trigger_type` 现在只回传，不按它切换规则。概设示例是 kafka / hand，没有写机动车各审核节点传什么。接口留了字段，节点与规则的对应还要补，否则调用方无法知道该传哪个值。
